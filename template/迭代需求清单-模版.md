# 迭代需求清单（模版）

> **用途**：作为迭代需求输入源，驱动 `docs/prd/V{版本号}/` 下 **原始页面需求设计**（仅新增页）、**页面需求与交互规格**、**需求规格说明书（SRS）** 等下游文档。  
> **定稿命名**：`docs/prd/V{X.Y.Z}/ATO_V{X.Y.Z}-需求清单.md`（或团队约定的 `ATO_V{X.Y.Z}迭代需求清单.md`，全库统一即可）。  
> **工作稿**：评审、对比阶段可使用 `ATO_V{X.Y.Z}-需求清单-补全稿.md`；**定稿后合并回正式文件名**，避免长期双文件并存。  
> **政策真源**：是否编写「原始页面需求设计」由 **`.cursor/rules/raw-page-design-from-v100-template.mdc`** 根据 §2.1 **类型** 列推导（**新增**→写；**改动存量**→不写；**存量重构**→须在备注明示并单独评审）。  
> **从 Excel 生成**：使用 **`prompt/迭代需求清单-从Excel生成与质量检测.md`**（配套 **`.cursor/rules/iteration-backlog-from-excel.mdc`**），一次完成清单 MD + 同目录 **`…-需求清单-质量检测报告.md`**。  
> **编写指导**：§2「需求说明书写要点」等 **【编写指导】** 段落仅供人写清单时对照，**生成物不得复制**（见该段起止标记）。

**需求说明书写要点**（编写指导）

> **目的**：本列是 **原始页面需求设计**（仅 §2.1 **类型=新增** 页）、**《页面需求与交互规格》**、**《需求规格说明书》** 的共同输入。须写到测试/评审可判定 **通过与否**；**禁止**用「优化体验」「详见设计」等空泛句代替。  
> **分工**：清单写 **业务规则与验收边界**；组件尺寸、动效、精确文案等可下放页面 PRD（见 §7 速查）。  
> **复杂域**（字段 >15、多状态机、跨 REQ 同一交互）：主 REQ 写摘要 + **§6 附录** 展开；从 REQ 写「见主 REQ / 附录 X」。

#### 共通（新增与优化均须覆盖）

| 维度 | 须在「需求说明」中写清的内容 |
|------|------------------------------|
| **入口与范围** | 用户从哪进入（菜单/按钮/路由）；本 REQ 覆盖哪一块能力（单页 / Tab / 弹层 / 列表行操作） |
| **行为规则** | 触发条件 → 系统做什么 → 结果反馈（成功/失败/阻断/继续） |
| **数据与依赖** | 关键字段数据来源（如 RDMS、基础数据、手工）；与上下游模块的约束（不可改字段、联动规则） |
| **边界与例外** | 空态、无权限、重复提交、并发、失败是否阻断后续步骤等 |
| **验收可测** | 至少 1～3 条可判定条文（含数字/枚举/禁止项时写死，如「最多 2 条」「同产品下唯一」） |
| **主从 REQ** | 多 REQ 共用一套交互时：主 REQ 写规范摘要；从 REQ 只写 **入口差异**（如底 Drawer vs 右 Drawer） |

**书写禁忌**：不得仅写需求 ID 或「以清单为准」；不得编造 Excel/清单未给出的口径；待定用 **`【待产品确认】`**，定稿前须清零。

#### 新增需求（`需求类型` = **新增**）

对应 §2.1 **类型=新增** 时，还须支撑 **原始页面需求设计** 的 `0.1` / `## 3` 页面小节，下列条目 **优先写在清单**（字段多时可进 §6 附录，§3 保留摘要 + 指针）。

| 书写要点 | 说明与示例 |
|----------|------------|
| **路由与载体** | 主路径、Tab query（`?tab=`）、动态段（`:id` 含义）、子路由、**页内 Modal**（注明无独立路由）；与 §2.1、「关联页面/入口」一致 |
| **页面结构块** | 列表 / 表单 / 详情 / 统计各有哪些 **区域或块**（如日报正文仅 3 块：今日进展、风险、明日计划） |
| **字段级定义** | 字段名、控件类型（输入/下拉/日期/列表）、**必填**、最大长度、默认值、**枚举取值** |
| **唯一性与不可编辑** | 如「同产品下日报名称唯一」；创建后不可改的字段列表 |
| **状态与操作矩阵** | 各状态下允许/禁止的操作（编辑、删除、提交、启停定时任务等） |
| **列表列与行操作** | 列表展示列名（避免歧义列名）、行级按钮及显示条件 |
| **流程与状态流转** | 草稿→已提交、启动/停止、发送模式（定时/手动/组合）及 **是否支持撤回** |
| **权限与角色** | 谁可见、谁可编辑、管理员专属能力（如设置 Modal） |
| **通知与后台** | 定时规则（如每周固定时刻）、收件人（固定邮件组等）；**是否涉及 UI=否** 时写清触发条件与「未提交」定义 |
| **P6 / 原型边界** | Mock 发送、无真实 SMTP 等写入 §2.4 或本条，避免下游误以为已含生产对接 |

**新增 · 可下放至页面 PRD（清单可不写细）**：Drawer 宽高与动画、列宽排序、图标与空态插图、Toast  exact 文案、图表形态与导出格式（除非产品已定统计维度与指标）。

#### 优化需求（`需求类型` = **优化**）

对应 §2.1 **类型=改动存量**；**不**单独生成原始页面需求设计整页结构，清单须写清 **相对改前** 的增量，供 **页面 PRD 迭代变更摘要** 与 **SRS** 使用。

| 书写要点 | 说明与示例 |
|----------|------------|
| **改前 / 改后** | 当前行为一句话 + 目标行为一句话（评审时能对比） |
| **改动位置** | 存量页面哪一块：步骤编辑区 / 断言表 / 列表工具栏 / 报告详情 Drawer 等；写清 **关联页面/入口** |
| **控件与交互增量** | 新增列名（如「失败阻塞」）、新增控件（逻辑与/或、批量标签）、操作路径（批量选 → 标签 → 新增/移除） |
| **规则与默认值** | 默认勾选/隐藏条件（如仅 1 条条件时隐藏逻辑选择）、数量上限、覆盖 vs 追加（批量标签是覆盖还是追加且不重复） |
| **兼容与数据** | 旧数据如何展示/迁移（如 P5 单条件兼容为 1 条 + 默认与）；是否改变保存结构 |
| **与关联 REQ 关系** | 若 007/008/009 共用交互：写明 **从属主 REQ** 及 **容器/入口差异**；细则放附录 |
| **运行/结果侧** | 断言失败是否阻塞、异常是否同列控制、继续执行时结果页如何 **可识别标记** |
| **非 UI 优化** | 路径规则（`upload/{filename}`）、失败是否阻断步骤、列表是否立即可见等 **无新页** 的后端/目录规则 |
| **回归范围** | 哪些既有能力须 **保持不变**（写「与改前一致」或「与现有 xx 联动规则不变」） |

**优化 · 可下放至页面 PRD**：具体像素、组件库选型、代码高亮层级；内网原型 URL 仅作参考（非唯一真源）。

## 5. 使用约束

1. 业务模块字段须对齐 **`.cursor/rules/requirements-module-split.mdc`**；**新模块**定稿前完成登记。  
2. 生成 PRD / 页面规格 / SRS 时，默认输出至 **`docs/prd/V{X.Y.Z}/`**。  
3. 未收到「允许合入全量（`docs/requirements/`）」明确指令前，**不得**写入 `docs/requirements/`。  
4. **是否涉及 UI = 否** 时，仍须在「需求说明」中写清业务流程、触发条件、验收标准。  
5. **原始页面需求设计**：纳入范围见 **`raw-page-design-from-v100-template.mdc`**；§2.1 **不**维护「是否纳入原始页面需求设计」列。  
6. 存在 **§6 附录** 时，相关 REQ 以附录为字段/状态/交互真源；§3「需求说明」可摘要 + 指向附录。  
7. 每次迭代结束后保留本清单，用于需求追溯、验收对账及下一迭代输入。  
8. **定稿**：评审通过后更新 **状态** 为「已确认」，合并工作稿至正式文件名；维护人、日期以定稿为准。
